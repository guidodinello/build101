# Security, privacy and compliance

This doc covers the security, privacy and compliance dimension of the 2026-10-19 product and codebase audit of Neitor AI (see [README.md](README.md) for the full audit and [summary.md](summary.md) for the cross-dimension synthesis). The code was read at commit `dc0bc01`. Every finding below was checked by an independent adversarial reviewer against the code and the cited sources; "confirmed" means the reviewer agreed, and "adjusted" means the reviewer corrected the severity or details. The severities and recommendations here are the corrected ones. Live checks against the Supabase project were read-only, and this doc deliberately omits the project ref, keys, tokens and step-by-step exploit paths.

## Summary

Some of the core security controls are well built:

- The Kapso webhook checks a constant-time HMAC over the size-capped raw body ([kapso_webhook.py:12-17](../../../backend/app/channels/kapso_webhook.py), [router.py:54-69](../../../backend/app/channels/router.py)).
- Magic-link tokens are 256-bit and stored only as hashes ([links.py:14,22](../../../backend/app/onboarding/links.py)).
- Approval is decided in code, as [ADR 0007](../../decisions/0007-approve-every-post.md) requires, and publishing only goes through the Post that the code-computed Approval names ([approval.py:111-161](../../../backend/app/conversation/approval.py), [publish.py:84-89](../../../backend/app/posts/publish.py)).
- Every tool and button lookup is scoped to the sender's phone, so no cross-tenant path was found ([chat.py:551](../../../backend/app/conversation/chat.py), [button_router.py:154-156](../../../backend/app/conversation/button_router.py), [queue.py:42-46](../../../backend/app/jobs/queue.py)).
- `/api/render` accepts only data URIs, so it has no SSRF ([spec.ts:44,77-82](../../../frontend/lib/post-render/spec.ts)).
- Gemini calls run with `store=False` ([client.py:234](../../../backend/app/llm/client.py)), a scan of 148 commits found no secrets in git history (audit observation, 2026-10-19), and CI runs with least-privilege permissions ([ci.yml:24-25](../../../.github/workflows/ci.yml)).

The most serious risks sit around that core, and three must be fixed before any real Owner uses the product:

- **Supabase is open to the anon key** (SEC-1). A live check found RLS off on 19 public tables, and the `anon` role has SELECT and UPDATE on `businesses`, `magic_links`, `conversation_steps` and `owner_notes`. The project ref is published in the public repo.
- **Every Owner publishes to one shared company Instagram account** (SEC-2, [ADR 0024](../../decisions/0024-mvp-single-demo-instagram-account.md)). Anyone who can reach the bot can publish to it.
- **There is no privacy notice, consent capture, terms page, URCDP registration or data-deletion path** (SEC-3, SEC-6). Ley 18.331, the Meta Platform Terms and the WhatsApp Business Messaging Policy require these.

Next come abuse and cost controls. No sender allowlist, rate limit or persistent quota exists: the Free tier's 3-Post cap and the daily design cap are not durable, and the design cap lives in memory and resets on every deploy (SEC-4). The wizard's upload cap can be bypassed with upload, complete and delete cycles, which fills Storage, triggers Gemini analyses and can exhaust the memory of the single 1 GB instance (SEC-5).

After those: magic-link tokens leak into uvicorn and Vercel request logs and into the OAuth state, and links live 7 days, are never revoked and stay readable after completion (SEC-7, SEC-8). The Instagram OAuth state is not bound to the browser that started it, an account-linking CSRF that becomes serious once DM scopes ship (SEC-9). Instagram tokens are stored in plaintext, production secrets are shared with dev machines, and the Gemini key may be on the unpaid tier, whose terms let Google use the data (SEC-10, SEC-11). Most fixes are small (S): one migration, an allowlist, log filters, link revocation and a cookie-bound OAuth state.

## Findings

### SEC-1: Supabase Data API exposes every table to the anon role: RLS off on 19 public tables, anon has SELECT and UPDATE

- **Severity**: high · **Effort**: S · **Confidence**: high · **Verified**: adjusted
- **Evidence**: RLS is enabled only on `social_accounts` ([0002_instagram_import.sql:11-13](../../../backend/migrations/versions/0002_instagram_import.sql)); `businesses` (with `owner_phone`) and `magic_links` have no RLS or REVOKE in any migration ([0001_initial.sql:4,31](../../../backend/migrations/versions/0001_initial.sql)); `conversation_steps` and `owner_notes` are created without RLS ([0003_conversation_memory.sql:4,15](../../../backend/migrations/versions/0003_conversation_memory.sql)). The live Supabase security advisor reports `rls_disabled_in_public` at ERROR level on 19 tables, including `businesses`, `magic_links`, `conversation_steps`, `owner_notes`, `brand_brains`, `posts` and `jobs` (audit observation, 2026-10-19, read-only). Live read-only SQL shows `has_table_privilege('anon', ..., 'SELECT')` and `'UPDATE'` are true for `businesses`, `magic_links`, `conversation_steps`, `owner_notes` and `brand_brains` (audit observation, 2026-10-19). The `assets` bucket is private (positive; audit observation, 2026-10-19). The project ref is committed in [.mcp.json:5](../../../.mcp.json) and the repository is public (audit observation, 2026-10-19). Supabase documents this lint in [0013 rls_disabled_in_public](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public) (read 2026-10-19).
- **Problem**: The backend connects as the table owner and never uses PostgREST, but Supabase still serves the `public` schema through its Data API to anyone holding the anon (publishable) key, and Supabase treats that key as public by design. With it, anyone could read every Owner's phone number, full conversation history (`conversation_steps`), Owner notes, Brand Brain and Catalog. They could also insert or update rows in `magic_links`, which is enough to take over any Owner's onboarding wizard, Instagram connect included. The public repo already gives the project ref and the production backend URL; the only missing piece is the anon key, one leak away (a future supabase-js use in the frontend, a teammate's `.env`, a screenshot).
- **Recommendation**: Ship migration 0004 before the pilot: enable RLS on every public table, `alembic_version` included; revoke all on tables, sequences and functions in schema `public` from `anon` and `authenticated`; alter the default privileges so future tables are closed too; and remove `public` from the Data API's exposed schemas. Update [data-model.md:403](../../architecture/data-model.md) so it no longer says RLS can stay off while the backend is the only client. Add a CI or nightly check that fails on `relrowsecurity = false` or on the advisor's `rls_disabled_in_public`. Rotate the anon key only if it was ever shared.
- **Impact**: Closes a full read and write exposure of every Owner's personal data (phones, chats, notes) and a magic-link takeover path before the pilot. It is the main security measure that [Ley 18.331](https://www.impo.com.uy/bases/leyes/18331-2008) art. 10 and the [Meta Platform Terms](https://developers.facebook.com/terms/) 6.a.i expect (read 2026-10-19).
- **Verifier note**: Checked live and read-only: the advisor reports `rls_disabled_in_public` at ERROR level on 19 tables, `has_table_privilege` shows `anon` holds SELECT, INSERT and UPDATE on every public table, and the authenticator role sets no `pgrst.db_schemas` override, so `public` is exposed through the Data API. The magic-link takeover path is real. Two things the auditor missed: (1) this is a documented hackathon decision, since [data-model.md:403](../../architecture/data-model.md) keeps RLS off because the backend is the only database client and says to turn it on "before any client talks to Supabase directly", and that rationale is wrong because the anon key grants access whether or not the app uses it; (2) it is not exploitable today, because the anon key is not in the repo, `frontend/.env.example` or any frontend code (there is no supabase-js; [upload.ts](../../../frontend/lib/upload.ts) only mimics its body shape). `social_accounts` has RLS with no policies, so the Instagram tokens there are not exposed. High, not critical: a latent exposure that needs one key leak, on personal data, with a trivial fix.
- **Related**: [ARCH-16](backend-architecture.md)

### SEC-2: All Owners publish to one shared company Instagram account; anyone who reaches the bot can post to it

- **Severity**: high · **Effort**: M · **Confidence**: high · **Verified**: adjusted
- **Evidence**: `account_id` is the single `ZERNIO_ACCOUNT_ID` for every sender ([publish.py:104-110](../../../backend/app/posts/publish.py)); one demo profile and account come from env ([config.py:56-62](../../../backend/app/config.py)); "Every Business in the demo publishes to the same Instagram account" ([ADR 0024:21](../../decisions/0024-mvp-single-demo-instagram-account.md)); any phone that writes gets a Business row and an onboarding link ([onboarding.py:64-69](../../../backend/app/conversation/onboarding.py)); moving publishing to the Owner's own account is still an open question ([open-questions.md:94](../../open-questions.md)).
- **Problem**: ADR 0024 was a demo shortcut, and it is still the production code path. In a pilot, Owner A's approved Posts would land on Neitor's demo account, not on A's. Once WhatsApp runs on a production number instead of the Kapso sandbox, any stranger could onboard, have Gemini generate images and captions, approve, and publish to an Instagram account the company owns. ADR 0007 proves the sender approved the Post; it does not prove the sender is entitled to publish to that account. The sandbox's recipient limit is the only thing preventing this today.
- **Recommendation**: Treat reversing ADR 0024 as a pilot blocker; this needs an ADR superseding [ADR 0024](../../decisions/0024-mvp-single-demo-instagram-account.md). Resolve the publishing target per Business from `social_accounts`: either a Zernio profile per Business through the existing `ensure_profile`/`connect_url`, or our own Meta app with `instagram_business_content_publish`, as asked in [open-questions.md:94](../../open-questions.md). Return `need_ig` when no publishing account is connected. Before any non-sandbox number goes live, add a sender allowlist in `OnboardingGate` and a publish kill switch.
- **Impact**: Stops third parties from posting under the company's brand (reputational, Meta-policy and legal exposure), and makes the pilot publish where the Owner actually expects.
- **Verifier note**: Confirmed in the code: `PostPublisher._start` always uses the single env `ZERNIO_ACCOUNT_ID`, `OnboardingGate` creates a Business for any sender, and no allowlist exists anywhere (a grep for allowlist, allowed_senders and similar finds nothing). Not an oversight: ADR 0024 (status proposed) chose it deliberately and documents how to reverse it, and open-questions.md:94 tracks it. Stranger abuse is gated today: [backend/README.md:78](../../../backend/README.md) says `WHATSAPP_BOT_NUMBER` is the shared Kapso sandbox number, which "only answers phones with an active sandbox session", and our own Meta app reads only Instagram testers while in development mode. The real pilot issue is product correctness (Owners' approved Posts would land on Neitor's demo account); abuse by strangers becomes possible only after a move to a production number. High, not critical.
- **Related**: [PRD-1](product.md), [BUG-1](bugs-reliability.md), [ARCH-4](backend-architecture.md), [GRW-2](growth-pricing-market.md), [GAP-1](cross-cutting-gaps.md), [OPS-3](platform-ops.md)

### SEC-3: No privacy notice, consent capture, terms page or URCDP registration before collecting Owners' data

- **Severity**: high · **Effort**: M · **Confidence**: high · **Verified**: adjusted
- **Evidence**: The [frontend routes](../../../frontend/app) are only `page.tsx`, `o/[token]`, `api/render`, `dev` and `mock-api`, with no `/privacidad` or `/terminos` (git ls-files, audit observation, 2026-10-19); the footer has no legal links ([site-footer.tsx:53-54](../../../frontend/components/landing/site-footer.tsx)); the welcome message has no notice or link ([messages_es.py:60-65](../../../backend/app/copy/messages_es.py)); the phone is stored on the first message with no consent recorded ([onboarding.py:67-69](../../../backend/app/conversation/onboarding.py)); the backend runs in us-east4 (Virginia) and Supabase in sa-east-1 ([ADR 0017:37](../../decisions/0017-backend-host-railway.md), [backend/README.md:44](../../../backend/README.md)), and Google Gemini, Kapso, Zernio and Vercel also process data. Legal sources: [Ley 18.331](https://www.impo.com.uy/bases/leyes/18331-2008) arts. 9 (free, prior, express, informed, documented consent), 13 (information duty), 23 (international transfer needs adequacy or unequivocal consent) and 28-29 (register databases); [Decreto 64/020](https://impo.com.uy/bases/decretos/64-2020) art. 4 (breach notification to URCDP within 72 h); [Meta Platform Terms](https://developers.facebook.com/terms/) 4.a-4.b (public privacy policy URL set in the app dashboard, explaining the data and how to request deletion); [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/es-la/policy/) §3 ("mantener una política de privacidad publicada"). All read 2026-10-19.
- **Problem**: From the first real Owner, Neitor is the controller of personal data: the Owner's phone and name, voice transcripts, photos (possibly of employees or customers), conversations and Instagram content. All of it is sent to processors outside Uruguay (US, Brazil, Google's global facilities). Ley 18.331 requires informed, documented consent, an information notice, a legal basis for international transfers and registration of the database with URCDP. Meta App Review (roadmap Phase 2) and WhatsApp policy both require a published privacy policy. None of these exist, and there is no breach-response process for the 72-hour URCDP notice.
- **Recommendation**: Before the first real Owner: (1) publish `/privacidad` and `/terminos` covering data, purposes, sub-processors and countries, retention, rights and contact, plus the Owner's warranty over the photos they upload; (2) link them from the welcome message and the wizard; (3) record `consented_at` and `policy_version`; (4) register the database with URCDP; (5) set the privacy URL in the Meta app; (6) keep a one-page incident runbook: start containment within 24 h, notify URCDP within 72 h. Rely on contract performance (art. 9 lit. D, art. 23 lit. B) plus documented consent as the legal basis, and have a Uruguayan lawyer review it once.
- **Impact**: A legal precondition for processing the first real Owner's data. It also unblocks Meta App Review, Business Verification and a production WhatsApp number, and avoids URCDP sanctions under [Ley 18.331](https://www.impo.com.uy/bases/leyes/18331-2008) art. 35 (read 2026-10-19).
- **Verifier note**: Confirmed: the frontend routes have no privacy or terms page, the footer has no legal links, the welcome message has no notice, and a grep for privacidad, privacy or consent finds nothing in the code, roadmap or open questions. Re-checked on IMPO: art. 13 and arts. 28-29 are as stated, Decreto 64/020 art. 4 sets the 72-hour URCDP notification and art. 3 sets 24 h to start containment, and WhatsApp policy §3 requires a published privacy policy. One overstatement: art. 9 lit. D exempts data "derived from a contractual relationship… necessary for its performance", and art. 23 lit. B allows transfers "necessary for the performance of a contract" with the data subject, so unequivocal consent for international transfers is not strictly required; documented consent is still the safest basis. For a hand-picked pilot the enforcement risk is modest, but a public privacy policy URL gates Meta Live mode, App Review and a production WhatsApp number. High, not critical.
- **Related**: [FE-2](frontend.md), [PRD-8](product.md), [DOC-5](docs-process.md), [GAP-4](cross-cutting-gaps.md); SEC-6 in this doc

### SEC-4: No sender allowlist, rate limit or durable quota: one WhatsApp number can burn the Gemini and Kapso budgets

- **Severity**: medium · **Effort**: M · **Confidence**: high · **Verified**: adjusted
- **Evidence**: Any sender creates a Business, with no allowlist ([onboarding.py:64-69](../../../backend/app/conversation/onboarding.py)); the daily design cap is a per-process dict, reset on every deploy, and only `style='design'` counts ([maker.py:105,184-191](../../../backend/app/posts/maker.py)); `MAX_POSTS_PER_DAY=5` ([config.py:44](../../../backend/app/config.py)); `plan` and `monthly_post_quota` are marked "not enforced" ([0001_initial.sql:20-21](../../../backend/migrations/versions/0001_initial.sql)); every text is an Orchestrator turn with up to 5 model steps and no per-sender rate limit ([chat.py:61,169-177](../../../backend/app/conversation/chat.py)); Free is 3 Posts a month and enforcement is deferred until billing exists ([ADR 0031:16,25](../../decisions/0031-pricing-free-basic-pro.md)); US$0.30-0.40 per 5-slide carousel at 2K ([open-questions.md:58](../../open-questions.md)); Kapso free plan is 2,000 messages a month ([integrations.md:9](../../architecture/integrations.md)); token usage is logged but not tied to a Business, and the `agent_runs` table is never written ([client.py:246-255](../../../backend/app/llm/client.py)).
- **Problem**: Once the bot runs on a production number, anyone can onboard and then send unlimited text, voice and photo turns. Each turn runs Gemini with medium thinking and up to 5 steps. "Photos as they are" Posts, caption revisions and chat are uncapped. The 5-designs-a-day cap is per process and resets on each deploy, and the Free tier's 3-Posts-a-month promise is enforced nowhere. Nothing stops a spammer from exhausting Kapso's 2,000-message plan, which takes WhatsApp down for every Owner. Because usage is not attributed to a Business, an abuser cannot be spotted. ADR 0031 defers enforcement to billing in Phase 2, which is too late.
- **Recommendation**: For the pilot, add an `ALLOWED_SENDERS` allowlist in `OnboardingGate` (unknown numbers get one fixed reply and no LLM call), and move to a paid Kapso plan before going beyond the sandbox. Before a public number: (1) persist usage per Business and month (write `agent_runs` with `business_id`); (2) enforce the Free quota from ADR 0031 in `PostMaker._start`, replacing the in-memory dict; (3) add a per-sender inbound rate limit; (4) set GCP budget alerts and quotas. ### SEC-18: Frontend has no security headers; dev routes are guarded only by env flags

- **Severity**: low · **Effort**: S · **Confidence**: high · **Verified**: adjusted
- **Evidence**: No `headers()` ([next.config.ts:3-20](../../../frontend/next.config.ts)); bearer token in the URL ([wizard page.tsx:20-24](../../../frontend/app/o/[token]/page.tsx)); only env flags gate the dev routes ([mock-api route.ts:3,8](../../../frontend/app/mock-api/[...path]/route.ts), [preview.ts:1-3](../../../frontend/lib/post-render/preview.ts)). ### SEC-19: Prompt-injection posture: the approval gate is solid; plan for third-party text before Pro

- **Severity**: low · **Effort**: S · **Confidence**: medium · **Verified**: confirmed
- **Evidence**: Only the Post named by the code-computed Approval publishes, so ADR 0007 holds ([approval.py:111-161](../../../backend/app/conversation/approval.py), [publish.py:84-89](../../../backend/app/posts/publish.py)); Owner tools are refused on event turns ([chat.py:540-542](../../../backend/app/conversation/chat.py)); tenant scoping keys every lookup by the sender, and no cross-tenant path was found ([chat.py:551](../../../backend/app/conversation/chat.py), [button_router.py:154-156](../../../backend/app/conversation/button_router.py), [queue.py:42-46](../../../backend/app/jobs/queue.py)); business facts, Owner notes, Catalog and trend notes are inserted without escaping ([context.py:101-114](../../../backend/app/conversation/context.py)); trend notes come from third-party websites via `url_context` and `google_search` ([niche_analyst.py:27](../../../backend/app/agents/niche_analyst.py)); an escaping `tagged` helper exists and the agents use it since PR #60 ([prompts/\_\_init\_\_.py:10-15](../../../backend/app/prompts/__init__.py)).
