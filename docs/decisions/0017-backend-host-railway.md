# 0017: Backend hosted on Railway

- Date: 2026-10-17
- Status: proposed

## Context

The backend needs one always-on container ([ADR 0005](0005-single-instance-in-process-jobs.md)) that builds `backend/Dockerfile` and exposes public HTTPS for the WhatsApp webhook ([ADR 0002](0002-whatsapp-cloud-api-channel.md), through Kapso per [ADR 0020](0020-whatsapp-via-kapso.md)). It no longer runs Chromium: post images come from a third-party image service ([ADR 0018](0018-ai-image-generation-service.md)), so the container only runs Python, light image resizing (Pillow) and HTTP calls, and the Trial's 1 GB of RAM per service is enough. The goal for the hackathon is a working deploy in hour 1 with minimal setup. Tenki was listed as the default host, but there is no evidence it offers app hosting; the team only uses Tenki as the PR reviewer.

Options considered (read 2026-10-17):

- **AWS ECS/Fargate + S3**: VPC, load balancer, ECR, IAM and task definitions are too much setup for 24h. S3 is redundant with Supabase Storage ([ADR 0003](0003-database-supabase-sqlalchemy.md)). New accounts no longer get the 12-month free tier; they get $100–200 in credits for up to 6 months ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/07/aws-free-tier-credits-month-free-plan/)).
- **Render free**: spins down after 15 minutes without inbound traffic and takes up to a minute to wake ([Render docs](https://render.com/docs/free)), which loses in-process jobs and delays webhooks.
- **Supabase Edge Functions**: 256 MB memory, 2 s CPU time, 150 s (free) / 400 s (paid) wall clock ([Supabase docs](https://supabase.com/docs/guides/functions/limits)), and a Deno runtime instead of Python, while the backend is Python ([ADR 0001](0001-backend-python-fastapi.md)).
- **Vercel Functions / serverless in general**: timeouts and no work after the response, while posts are generated by in-process background jobs ([ADR 0005](0005-single-instance-in-process-jobs.md)).
- **Railway**: builds a Dockerfile from the repo, gives an HTTPS domain, does not sleep. Plans ([Railway docs](https://docs.railway.com/pricing/plans), [free trial](https://docs.railway.com/pricing/free-trial)):
  - Trial: one-time $5 grant, up to 30 days, 1 GB RAM per service; unverified accounts get restricted outbound network.
  - Free (after the trial): $1/month credit, 0.5 GB RAM per service.
  - Hobby: $5/month including $5 of usage, up to 48 GB RAM per service.

## Decision

Host the backend on **Railway**: one service, root directory `backend/`, built from `backend/Dockerfile`, one replica, with a Railway-generated HTTPS domain. The database and storage stay on Supabase and the frontend on Vercel.

Start on the **Trial**, with the account verified through GitHub (the Limited Trial restricts outbound network, which would block calls to Anthropic, Kapso, Gemini, OpenAI, Zernio and Supabase). Upgrade to **Hobby** when any of these happens: the service runs out of memory under the Trial's 1 GB cap, the 30-day trial or its $5 grant is about to run out before the demo, or the app has to stay up after the hackathon.

## Consequences

- Free on the Trial; about $5 per month on Hobby. RAM is billed at $10 / GB / month.
- The Trial counts from account creation, so check its end date against the hackathon date.
- Deploys on every push to `main`; no infrastructure code to maintain.
- The deploy must be verified in hour 1: `/health` over HTTPS and the WhatsApp webhook reaching the backend.
- Moving to AWS or another container host later is cheap: the app is a plain Docker image configured by environment variables.
